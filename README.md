# PICC-platform

院內 PICC 建案、預約施打與施打回報平台。新版以 Supabase 作為正式資料後端；本機提供獨立的假資料預覽，n8n 的 LINE 群組通知留待後續串接。

## 首頁與三個手機入口

網域根目錄 `/` 依畫面寬度分流：電腦開啟完整的 `/workspace/`，手機（寬度 680 px 以下）開啟 `/picc-create/`。直接使用以下三個網址時，會保留各自的簡易操作畫面。

| 網址路徑 | 內容 |
| --- | --- |
| `/picc-create/` | 填寫床號、病歷號、姓名與選填備註；支援自起單、自回報。進入自回報後不顯示「改為一般建案」按鈕；成功送出後顯示該病人的完成畫面，不自動回到起單表單。 |
| `/picc-booking/` | 只列新開案，選擇施打人後預約；可取消施打。 |
| `/picc-report/` | 列出已接單的等候施打案件，顯示接單者與等待時間；使用單一「施打回報」按鈕填表完成。 |

**手機入口與電腦工作站均不需要個人登入或身分認證。** 開啟後直接操作，施打者由下拉名單選擇。操作歷程分別記為「內部共用入口（未驗證操作者）」與「內部共用工作站（未驗證操作者）」；個人施打量依選定的實際施打者與完成日期計算。電腦版包含進行中工作台、案件管理、成效指標、CSV 匯入／匯出與成員名單。

手機版採精簡頁首與較短的表單間距；一般起單的「送出」與「自起單・自回報」同列顯示，輸入框保留 16px 字級，頁面底部預留捲動空間。預約／回報卡片集中顯示姓名、床號、病歷號、案號與目前狀態；接單者、等待時間及起單時間緊密排列，長備註預設收合，可點「查看備註」展開完整內容。困難放置提醒仍直接顯示。原有起單、接單、回報、取消與歷史保留規則沿用。完整前後對照見 [手機精簡版型](docs/mobile-compact-20261028.html)。手機實機畫面依使用者要求由使用者確認，未宣稱已完成實機驗收。

一般起單維持綠色；自起單・自回報採紫色主題，頁首標示目前模式，背景、表單、入口及送出按鈕一併區分。手機入口、回報彈窗及工作站的日期／時間欄位限制在表單寬度內，取消原生控制項與 fieldset 的最小內容寬度，日期時間內容靠左對齊。完整前後對照見 [自回報配色與時間欄位](docs/self-report-theme-20261028.html)；依使用者指示，畫面由使用者自行確認。

工作台使用全寬表格，欄位依序為：起單時間、病歷號／案件編號、病人姓名、床號、案件狀態、接單者、起單至今、操作。起單時間在上行呈現臺灣日期、下行呈現時分；病歷號粗體放大，案件編號在下行使用 14 px 字體，兩行間距縮小為 1 px。狀態使用可直接點選的頁簽，預設「所有案件」（涵蓋兩種進行中案件），可篩選「新開案、等候施打」。不顯示大型儀表板、側邊摘要或成員案件選單。已完成與已取消案件保留在「案件管理」。工作台移除「詳情」按鈕；接單後只顯示一個「施打回報」主要按鈕，開啟表單不會改變狀態，送出完整回報後才結案並計量。舊的待回報案件會併入等候施打，保留接單者、原日期與整併歷程；不增加退回流程。

新顯示名稱對應既有狀態代碼：`pending` 為新開案、`claimed` 為等候施打。`awaiting_report` 僅保留作舊資料相容，部署時併入 claimed；不再提供建立待回報狀態的操作。CSV 匯出附加「狀態代碼」，重新匯入時優先使用代碼。沒有代碼的舊 CSV 保留舊標籤含義（待預約 → pending、待施打／等候施打 → claimed、待回報 → claimed），避免因名稱更改而誤判歷史資料。

建置時會依 CSS／JavaScript 內容附上版本碼，HTML 回應不保留快取，讓既有瀏覽器在部署後取得同一版畫面與程式。

案件編號使用 `PICC-2610-001` 格式：臺灣時間的兩位年與月份，加上當月流水號。每月從 001 開始，同時起單由資料庫序列處理；取消、移除不回收號碼，重開使用新號並連結舊案，重送同一請求不重複取號。超過 999 時擴展位數。內部案件 UUID 保持不變，既有非測試歷史編號不批次變更。

成效指標以單一頁面整合個人施打量、案件成效、取消原因與處理時效，共用統計期間，預設本年度。兩張逐月圖上下各占滿版，兩張圖採共用刻度，並以水平虛線標示每月基本量 20 件，施打達標以完成施打量圖為準。每年固定呈現一到十二月；期間內無資料為 0，期間外為「—」，跨年度可橫向捲動。成效按起單日期選取同一批案件：完成施打率 = 完成 ÷（完成＋取消），未施打率 = 取消 ÷（完成＋取消）；仍進行中的案件另外列出，也提供取消占全部起單的比例。取消原因及起單至取消／完成回報的中位時間可協助觀察流程，不能單靠時間推定取消原因，也不代表穿刺技術成功率。未記錄日期的案件不補造等待時間。

合成驗收資料採八碼數字病歷號、四個中文字加 D 的病人姓名，以及最多三個中文字加 D 的成員姓名。批次標記保留於備註，方便日後辨識及移除；這些長度是測試資料規格，不限制正式姓名或病歷號輸入。

新增任務及自起單、自回報會在後端以去除前後空白的病歷號，檢查過去七日內的未移除案件（包含完成、取消案件）。如有重複，先回傳提示而不建立案件；使用者確認後仍可新增。確認提示保留填寫內容，改變病歷號會重新檢查。相同病歷號的併發起單在 PostgreSQL 交易內序列處理，重送仍維持冪等性。

施打位置提供右上臂、左上臂、左下肢、右下肢及其他。

血管選項提供 Basilic、Cephalic、Brachial 及其他，手機與電腦回報共用選項。既有資料庫可執行 `supabase/migrations/202610260001_allow_other_vein.sql`，只更新回報欄位檢核，不變更案件資料或權限。

手機自起單・自回報收到後端完成確認後，顯示起單與施打回報完成畫面，保留病人姓名、床號、病歷號、案件編號、實際施打者及臺灣完成時間。該次操作不再自動重設顯示空白起單表單；一般建案送出的既有流程維持不變。

新開案與等候施打均提供「取消施打」按鈕。取消會保留原單、原因與時間，從工作台移出並留在案件管理，且不計入完成施打量。需要再次施打時建立新單，連結原取消案件，原單不會重新開啟。統計使用臺灣時間；舊資料缺少完成日期時會保留「未記錄」，不以起單日期代替。桌機案件狀態以橘色（新開案）、藍色（等候施打）加強區別。

「預約」沿用原系統的成員接單流程，目前不含日期／時段排程。

手機、桌機與自起單・自回報的施打紀錄提供可調整的「施打時間（臺灣時間）」，開啟表單時預設目前年月日與時分，可補登先前實際施打的時間。完成施打量依這個時間與實際施打者計算；起單、接單、送出回報的稽核時間仍保留伺服器的實際操作時間。未提供時間的既有 API 呼叫預設伺服器目前時間；既有案件不會因更新而改動。已完成案件編輯仍須勾選「同時修正施打紀錄」，空白時間保留原紀錄。既有資料庫另套用 `supabase/migrations/202610260002_report_completion_time.sql`。

案件管理直接呈現日期查詢、匯入／匯出與案件清單，不再顯示「案件紀錄、團隊成員、通知紀錄」三個重複導覽頁簽；團隊成員與通知紀錄仍由側邊主選單進入。清單以放大加粗的「實際施打者」獨立欄位呈現施打量歸屬，接單者保留在詳情。尚未回報時顯示「尚未回報」，已完成但缺人員資料時顯示「未記錄施打者」，不以接單者代替。困難度與備註拆成獨立欄位，移除清單的管路／部位欄；完整施打內容仍保留在詳情。缺少困難度時顯示「未記錄」。

案件提供 Excel（.xlsx）及 CSV 匯出。Excel 以文字型別保存病歷號與案件編號，保留原有前導零，日期採臺灣時間並顯示 yyyy/mm/dd hh:mm。CSV 同樣將日期轉成臺灣格式；CSV 不含儲存格型別，直接用 Excel 開啟仍可能被自動判成數字，閱讀案件時建議使用案件 Excel。未任意補造或更改資料庫中的病歷號。

施打量 CSV 加入完成量與困難量的納入條件、分子／分母、比例代入算式及計入案件編號。案件成效 CSV 以逐項指標列出分子、分母、代入計算、日期基準、中位數計算方式與案件編號；分母為零時不把比例當成 0%。所有資料都在使用者點選匯出時讀取；Excel 元件僅在需要時載入，在瀏覽器內產生下載檔案。

## 舊版 MySQL 案件搬移

`scripts/prepare-legacy-mysql.py` 只讀取本機原始 JSON 備份，不會連線或變更舊 MySQL／n8n。它會在已被 Git 忽略的 `verification/` 目錄產生私人原始封存與正式啟用兩份 SQL；資料檔與 SQL 內含病人資料，不可提交版本庫。

搬移保留原病歷號、前導零、案件編號、備註及時間。依已確認的舊流程，沒有時區的舊時間解讀為臺灣時間。明確取消的備註轉為取消狀態，取消回報時間取原回報時間，不推定臨床決定取消的時間；實際施打者及完成時間不再填入取消案，原填報人與舊欄位完整保存在私人封存及歷程。缺少原因標記「未記錄（舊案）」；縮寫與含糊敘述只保留原文，不推定診斷。明確提及其他管路的原因可歸入「已有／改用其他管路」。

實際施打者依舊版 `operator` 對應，缺值時才參考 `completed_by`。成員以姓名精確比對，重複姓名先停止處理；不連結或新增 Supabase Auth 身分。原資料與轉換後案件用穩定識別碼對照，重複執行不增加案件、成員或歷程，並拒絕覆蓋既有不同來源案件。移轉前後應核對各狀態筆數、識別碼、備註與時間，原有新版案件不刪除。舊站後續新增或修改不會自動同步，切換前需另行處理差異。

目前依專案使用者確認保留外部免登入入口。這代表外部取得網址與前端公開連線資訊的人可透過共用 API 操作案件；它不提供院內身分驗證或私人存取保護。原始移轉封存表仍啟用 RLS 並撤銷匿名角色的直接存取。

## 驗證

在已安裝前端與 Python 相依套件的本機執行 `npm test`，會執行前端路由／流程、SQL 與角色、Excel 型別與臺灣時間，以及 Python 工作流程測試。HTTP 整合測試使用可拋棄的本機假資料庫；它不會對正式 MySQL、Supabase 或 LINE 寫入。正式站的操作驗證應另用有明確批次標記的假資料，完成後移除測試案件，不操作病人案件。


## 本機開啟

需求：Python 3.11 以上、Node.js 20 以上。

首次準備：

```powershell
python -m pip install --target .vendor -r requirements.txt
npm ci
npm run build:client
```

在 **Windows 檔案總管**雙擊 `開啟新版網站.cmd`。在程式編輯器點該檔案只會顯示內容，不會執行。

- 預設開啟：[PICC 平台首頁](http://127.0.0.1:8765/)，電腦自動進入完整工作站。
- [預約施打](http://127.0.0.1:8765/picc-booking/)
- [施打回報](http://127.0.0.1:8765/picc-report/)
- [完整管理工作站](http://127.0.0.1:8765/workspace/)：共用管理與統計，無個人登入。

測試後執行 `停止新版網站.cmd`，假資料會保留。Python 預覽只綁定這台電腦的 `127.0.0.1`；手機無法直接使用這個本機網址。

其他作業系統可執行：

```sh
python app.py --demo --port 8765
```

## Supabase 前後端

- `client/`：手機入口控制器與 Supabase 轉接器。
- `static/`：前端原始畫面與預覽資產。
- `dist/`：建置後可部署的靜態前端。
- `supabase/migrations/202610140001_picc_v2.sql`：資料表、狀態轉換、稽核、統計、權限與共用入口 API。
- `app.py`：本機示範伺服器，使用獨立 SQLite 假資料庫；正式版直接串接 Supabase，不需要用 Python 取代 Supabase。

Supabase 手機入口使用 `public.picc_v2_entry_api`，僅提供名單、建案、進行中清單、預約、回報與取消。完整工作站使用 `public.picc_v2_workspace_api`，提供案件管理、統計、成員維護與 CSV。舊的個人帳號 API `public.picc_v2_api` 保留相容，但目前畫面不使用。所有入口共用同一個資料庫交易引擎，避免重複計量與競爭接單。

### Coolify 串接步驟

1. 在 PICC-booking 專用資料庫套用 SQL migration。它使用獨立的 `picc_v2_private` schema，不修改舊 MySQL 或 n8n。
2. 在 Coolify 的 **PICC-Platform 網站 application** 加入 `NEXT_PUBLIC_SUPABASE_URL` 與 `NEXT_PUBLIC_SUPABASE_ANON_KEY`，設為 Runtime 可用。也接受 `SUPABASE_URL`／`SUPABASE_ANON_KEY` 別名。這些是前端公開連線設定，**不要填 service-role／secret key**。本機非示範模式可讀取被 Git 忽略的 `.env.local`；它不會提交到 GitHub。
3. 執行 `npm ci`、`npm run build:client`，重新部署網站。Python 服務的 `/assets/config.js` 在執行時產生設定，並將指定的 Supabase 網域加入瀏覽器連線政策；不必把 key 寫進程式庫。若改採純靜態 `dist/` 部署，則需先在 `static/config.js` 設定公開值後重新建置。
4. 在電腦工作站的「團隊成員」建立施打者名單，只需姓名與啟用狀態，不需要 LINE 或 Supabase Auth 帳號。
5. 先用假資料驗證建案 → 預約 → 回報、取消 → 重新建案與施打量。目前 `trialMode: true` 會顯示測試標示；備份還原與院內存取限制需另外驗收。

**免登入入口的存取範圍依賴網路限制。** 正式病人資料應置於院內網路或 VPN 的限制範圍，前端與 Supabase API 都必須受限；只有公開網址或把連結留在群組，不能限制外部存取。此階段僅供假資料驗收，LINE 通知尚未啟用。

本專案只包含新版程式與明確標示的合成測試資料，不包含病人資料、n8n API key、本機資料庫、登入憑證或執行紀錄。舊版 GitHub 專案、n8n 流程及病人資料未被修改。
